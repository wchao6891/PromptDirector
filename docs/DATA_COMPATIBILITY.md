# 数据兼容与升级门禁

PromptDirector 把正式发布的数据格式视为长期产品契约。应用版本、本机资料库结构版本和分享包格式版本彼此独立；应用更新不自动意味着数据格式变化。

## 兼容承诺

- 当前版本只导出最新分享包格式，但导入端永久支持每个已正式发布的分享包版本。
- 已知历史错误结构进入固定事故夹具；可恢复案例不因坏标签、坏媒体或同包其他坏案例而被拒绝。
- 本机资料库结构版本只增不减。迁移后必须保留案例、用户文字、用户标签、项目、回收站和创作会话等核心资产。
- 无法恢复的字节不会被伪造；程序跳过损坏对象、保留可用内容并返回逐项诊断。
- 涉及破坏性持久化变化时，至少保留一个正式版本的紧急回滚兼容窗口。

## 三条资料通道共用的安全合同

- 分享 ZIP、完整资料夹备份和加密同步共用同一套案例身份、媒体资源和清理规则；容器只负责读写文件或加密对象，不能各自解释资料结构。
- 导入和恢复必须先完成版本检查、迁移、逐项校验与计划确认，再一次性提交。一个损坏或不兼容的项目只影响自身，其他可恢复案例继续保留。
- 完整资料夹备份用于跨设备灾难恢复。安全合并保留本机资料并处理冲突；精确替换只接收完整备份，提交前建立可回退状态，容量不足或写入失败不得改变现有资料库。
- 完成标记有效但单个内容资源后来损坏时，恢复会降级为明确的救援流程，只隔离具体坏项并禁止精确替换；无法定位到具体坏项的解析错误仍停止，不以容错隐藏程序故障。
- 同步保留版本合并和可见冲突副本；只有完整内容指纹能够证明相同的不同编号案例才会收敛。缺少完整媒体哈希时保留两份，不猜测覆盖。
- 同步发现本机媒体确已缺失时会列出对应案例和文件，清理该坏引用后继续同步其他资料；媒体存储读取异常仍停止且不提交部分结果。
- 恢复提交与成功回执一起持久化。后台中断后，同一次操作只能继续原确认方案或读取已提交结果；资料已变化时要求重新预检，不能重复替换。回复丢失且结果无法确认时保留本次媒体，不按失败清理。
- 回退请求绑定用户确认的回退点和操作编号。同一次请求重发只返回原结果，不能把资料库再次交换回去。
- 媒体物理删除只能发生在资料状态提交成功之后。清理失败只允许留下额外字节，并在后续手动同步重试；活动资料、回收站、创作记录、暂存任务和恢复回退点仍引用的媒体不得删除。

## 权威清单

- `test/fixtures/compat/compatibility-matrix.json`：正式分享包和本机资料库结构清单。
- `test/fixtures/compat/provenance.json`：历史分享包夹具的来源与真实性边界。
- `tools/check-data-compatibility.mjs`：比较当前代码、上一正式标签和固定夹具的可执行门禁。
- `test/release_upgrade_e2e.py`：上一正式版与当前最终固定 ID 包共用 Chrome Profile 的升级演练。
- `test/local_upgrade_native_e2e.py`：旧版实际安装器对最终 ZIP 使用真实 Chrome 文件句柄写入原目录，再执行插件重启并核对身份、案例和媒体；临时目录权限预先授予，不替代日常 Chrome 原生授权验收。
- `test/library_import_interruption_e2e.py`：在提交前后实际停止 Chrome 后台，验证恢复接续、回执重放、媒体保留和回退幂等。

夹具是脱敏或重建的确定性回归证据，不冒充用户不可用的原始故障资料。取得新的真实事故样本后，应保留最小脱敏复现和来源说明，不能用新生成的正常文件替代故障证据。

## 修改数据结构时

1. 先判断变化属于应用行为、本机资料库结构还是分享包格式。
2. 只在持久化合同真实变化时增加对应数据版本。
3. 增加旧版本到当前版本的迁移和固定夹具；不得删除已发布版本。
4. 为案例、媒体、标签、项目、回收站和创作会话写出保留或显式丢弃规则。
5. 运行 `npm run check:compat`，再运行完整 `npm run verify`。

`npm run verify` 会在最终打包后执行上一正式版升级演练。GitHub 的 `Release safety` 工作流会对提交重复执行兼容检查、完整 Chromium E2E、两个 Chrome 包以及最终包升级演练。另一台设备上的真实事故备份仍需在取得文件后单独验收，重建夹具不能替代原文件证据。

## 共享媒体边界与迭代回归

资料库 ZIP、文件夹备份和恢复按实际文件与目标可用空间处理，支持 ZIP64。资料搬迁使用 `LIBRARY_TRANSFER_LIMITS` 表达浏览器可精确表示的字节和计数范围；网页采集与模型附件使用独立的资源预算。路径安全、文件声明大小、CRC、备份哈希和内容关系仍须完整校验。多 ZIP 逐包检查，原件在独立读取线程中按流校验并报告进度，导入资源以 Blob 句柄整组写入事务，失败整组回滚；取消检查应停止读取，正式导入明确失败应保持原资料库，并仅清理确定未被活动资料、暂存任务或回退点引用的本次资源；结果未知时先保留。

备份按钮在有效用户点击链路中立即打开目录选择器，随后检查资料，得到必要确认后才创建备份子目录。写入并回读验证通过后才生成完成标记；未写入完成标记的目录只能尝试救援恢复。

发布包实验室强制包含资料延续性场景：原生目录选择器有效/失效手势对照、GIF/AVIF 原件保留、完整/救援/失败备份、历史格式恢复、多 GB ZIP64 与压缩 ZIP 的实际字节往返以及手动同步。规模场景经默认 UI 导入、导出后由 Python 独立校验。重建夹具、原生 headless 取消、原设备真实事故包和用户安装版验收分别记录证据；最终安装版与真实事故包缺失时不能报告完整验收。

原文件字节与衍生封面分别保存。增加媒体类型或修改大小策略时，同时验证案例、回收站、临时参考、生成结果及附件；至少有一项“导出后走默认导入入口”的回归，不能只用生产者自行放宽参数的读回测试。

产品版本、持久数据格式与界面实现分开演进。新界面或运行机制可以替换，原始资料、用户编辑、来源归属、历史恢复能力和付费请求的真实状态必须继续有行为测试；版本号升级不等于擅自改变数据协议或固化当前布局。

安装目录授权仅保存在当前浏览器的升级器数据库，与可迁移案例资料分离；升级临时记录清理后仍保留已验证的安装位置。不能把旧设备目录句柄作为新设备的有效授权。目录名称不参与软件版本判断，也不以改名或搬库完成常规升级。

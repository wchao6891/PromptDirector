# 数据兼容与升级门禁

PromptDirector 把正式发布的数据格式视为长期产品契约。应用版本、本机资料库结构版本和分享包格式版本彼此独立；应用更新不自动意味着数据格式变化。

## 兼容承诺

- 当前版本只导出最新分享包格式，但导入端永久支持每个已正式发布的分享包版本。
- 已知历史错误结构进入固定事故夹具；可恢复案例不因坏标签、坏媒体或同包其他坏案例而被拒绝。
- 本机资料库结构版本只增不减。迁移后必须保留案例、用户文字、用户标签、项目、回收站和创作会话等核心资产。
- 无法恢复的字节不会被伪造；程序跳过损坏对象、保留可用内容并返回逐项诊断。
- 涉及破坏性持久化变化时，至少保留一个正式版本的紧急回滚兼容窗口。

## 权威清单

- `test/fixtures/compat/compatibility-matrix.json`：正式分享包和本机资料库结构清单。
- `test/fixtures/compat/provenance.json`：历史分享包夹具的来源与真实性边界。
- `tools/check-data-compatibility.mjs`：比较当前代码、上一正式标签和固定夹具的可执行门禁。
- `test/release_upgrade_e2e.py`：上一正式版与当前最终固定 ID 包共用 Chrome Profile 的升级演练。

夹具是脱敏或重建的确定性回归证据，不冒充用户不可用的原始故障资料。取得新的真实事故样本后，应保留最小脱敏复现和来源说明，不能用新生成的正常文件替代故障证据。

## 修改数据结构时

1. 先判断变化属于应用行为、本机资料库结构还是分享包格式。
2. 只在持久化合同真实变化时增加对应数据版本。
3. 增加旧版本到当前版本的迁移和固定夹具；不得删除已发布版本。
4. 为案例、媒体、标签、项目、回收站和创作会话写出保留或显式丢弃规则。
5. 运行 `npm run check:compat`，再运行完整 `npm run verify`。

`npm run verify` 会在最终打包后执行上一正式版升级演练。GitHub 的 `Release safety` 工作流会对提交重复执行兼容检查、完整 Chromium E2E、两个 Chrome 包以及最终包升级演练。
